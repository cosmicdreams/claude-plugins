# Action Card Template

Template for retrospective action cards generated by the retro-session skill.

**Storage**: Beads database at `.beads/retro.db` — no markdown files.
**Lifecycle**: lane-backlog → lane-approved → lane-in-progress → closed

---

## Creating a Card

```bash
bd --db .beads/retro.db create "skill: Add Phase 0 test design review to validate-patch" \
  -p 1 -t task \
  --labels "lane-backlog,target-skill,cat-improve,effort-m,session-YYYY-MM-DD,weight-high" \
  --description "$(cat <<'CARD'
## Finding
...

## Sources
...

## Recommendation
...

## Effort
...

## Priority
...
CARD
)"
```

**Priority mapping:** Critical → `-p 0`, High → `-p 1`, Medium → `-p 2`, Low → `-p 3`

**Label conventions:**
- `target-skill`, `target-memory`, `target-agent`, `target-claude-md`, `target-protocol`
- `cat-improve`, `cat-keep-doing`, `cat-learn`
- `effort-s`, `effort-m`, `effort-l`
- `session-YYYY-MM-DD` (ties card to its retrospective)
- `weight-critical`, `weight-high`, `weight-medium`
- `verification-required` (discipline cards; must append verification evidence before closing)

---

## Card Body

### Title (H1)

```
# [Target]: [Specific Action]
```

Examples:
- `# memory: Document Settings Tray HTMX patterns`
- `# skill: Add Phase 0 test design review to validate-patch`
- `# protocol: Create JSONL-MINING.md grep standards`
- `# agent: Add Drupal 11 entity validation patterns`

---

### Finding (What was observed?)

```
## Finding

[One paragraph describing the observation, without interpretation. Facts only.]

**Where observed**: [List of issues/tests/patterns where this appeared]

**Evidence count**: [Specific numbers, metrics, or citations]
```

Example:
```
## Finding

Validators spent 30% of session time waiting for DDEV instances to become available.
After validation completes, the DDEV container is left running, consuming resources
and delaying the next validator's start time.

**Where observed**:
- Issue #2901667: validator_agent-2 waited 3 min for instance
- Issue #2793141: validator_agent-3 waited 2.5 min for instance
- Issue #3543210: validator_agent-1 waited 2 min for instance
- Kanban board: 7 cards show validation_wait_time > 2 min

**Evidence count**:
- 3 explicit waits measured in JSONL timestamps
- ~30% of 405 session minutes spent in DDEV queue (from Phase 3 metrics)
- Idle ratio: 30% (target: <15%)
```

### Recommendation

```
## Recommendation

[Specific, actionable change proposed. Not vague. Implementable.]

**Change**: [Exactly what should be changed]
**Why this fixes it**: [How does this address the root cause?]
**Expected impact**: [What metric improves? By how much?]
```

Example:
```
## Recommendation

Implement immediate DDEV cleanup after validation completes, freeing resources
for the next validator to start fresh.

**Change**:
- Add `ddev stop` command to process-lifecycle skill SHUTDOWN phase
- OR add automatic cleanup to validate-patch skill after all tests pass
- Document in DDEV-CLEANUP.md protocol

**Why this fixes it**:
Currently validators wait 2-3 min for DDEV startup. With cleanup, instances
restart from cached state in 1-2 min. Removes 50-100 sec per validation handoff.

**Expected impact**:
- Idle ratio: 30% → 20% (reduce by 10pp)
- Agent utilization: 70% → 80% (increase by 10pp)
- Session throughput: ~7 issues/session → ~9 issues/session
```

```yaml
# skill: Add Phase 0 test design review to validate-patch

## Finding

Validators discovered 4 test design issues (not code regression) during validation,
requiring developer rework. These issues were caught by validators reviewing the
test code, not by running tests.

**Where observed**:
- Issue #2901667: Test assertion too broad, caught multiple unrelated behavior
- Issue #2793141: Mock object not properly initialized
- Issue #3070375: Missing assertion for error case
- Issue #3543210: Timeout too aggressive for async behavior

**Evidence count**: 4/7 issues (57%) had test design issues on first validation pass

## Sources

- **Agent feedback**: reviewer reported "Test Design" (V1) — category broken down as TEST_DESIGN root cause
- **Kanban observation**: 4 cards tagged with test_design_rework
- **Code inspection**: Pattern shows developers writing integration tests without error cases
- **Metrics**: First-pass rate 56%; analysis shows 50% of rework is test design, not code bugs

**Source count**: 3 independent sources = High consensus

## Recommendation

Add Phase 0 test design review to validate-patch skill, catching test issues
before running DDEV. This is "pre-DDEV validation" that developers can do
immediately after code submission.

**Change**:
- Update validate-patch SKILL.md to add Phase 0 (before DDEV launch)
- Phase 0: Review test code for: error cases, assertion clarity, mock setup, timeouts
- Quick checklist: All error paths tested? Assertions specific? Mocks initialized? Timeouts reasonable?
- If issues found, request developer revision; if clean, proceed to Phase 1 (DDEV testing)

**Why this fixes it**:
Test design issues are fast to catch (human review, 2-3 min) but expensive to fix
(rework, re-run DDEV, 15-20 min). Catching them before DDEV launch saves time.

**Expected impact**:
- First-pass rate: 56% → 70% (improve by 14pp)
- DDEV utilization: Less waiting for rework tests to run
- Session throughput: 7 issues → 8-9 issues

## Effort

**Estimate**: M (2-3 hours)

**Breakdown**:
- Design Phase 0 checklist: 30 min
- Update validate-patch SKILL.md with Phase 0: 45 min
- Document test design anti-patterns: 30 min
- Test with 2 issues: 30 min

**Risks**:
- Adding a phase could slow down validation if not efficient
- Risk mitigation: Make checklist fast (5 min max per review)

**Blockers**: None

## Priority

**Priority**: High

**Justification**:
- Affects first-pass rate (target improvement area)
- Quick fix (2-3 hrs)
- Low risk (additive, doesn't break existing flow)
- Expected 14pp improvement to first-pass rate
- Discovered by 3 independent sources (high consensus)
```

```yaml
# memory: Document tight test-fix-validate loop workflow

## Finding

The workflow where developers immediately handoff to validators, and validators
immediately re-test in the same DDEV instance (minimal cleanup between issues)
proved highly effective. This pattern produced a 56% first-pass rate and enabled
7 issues to complete in 6.75 hours.

**Where observed**:
- Session structure: DEVELOPING → VALIDATING flow with <5 min handoff
- All 7 developers handoff → immediate validator pickup
- DDEV persistence: Validators kept instances warm between issues
- Kanban board: No cards in "waiting for validation" state; validation starts immediately

**Evidence count**: 7/7 issues (100%) followed this workflow

## Sources

- **Agent feedback**: Developer and Validator both reported this in C1 (Biggest Success)
- **Process-improvement observation**: Identified tight loop as "Most effective interaction" (P2)
- **Kanban observation**: Cards flow continuously; no blockers between DEVELOPING and VALIDATING
- **Metrics**: First-pass rate 56% (reasonably high for Settings Tray conversion work)
- **JSONL analysis**: No handoff delay gaps; validation starts <2 min after developer marks code ready

**Source count**: 5 independent sources (Developer C1, Validator C1, Process P2, Kanban, Metrics, JSONL) = Critical consensus

## Recommendation

Document this workflow in MEMORY.md so future sessions intentionally preserve it.
Ensure future retrospectives check whether this pattern is maintained.

**Change**:
- Add to MEMORY.md under "Workflow Patterns": "Tight Test-Fix-Validate Loop"
- Describe: Developer → Immediate validator handoff → Same DDEV instance
- Expected impact on metrics
- Anti-patterns to avoid (batch validation, long gaps between phases)

**Why this fixes it**:
This pattern should be *explicitly preserved*, not accidentally lost. Documenting it
ensures new agents and team leads understand why this workflow matters.

**Expected impact**:
- Knowledge capture (no metric change, but prevents regression)
- Enables consistent 50-60% first-pass rate
- Prevents workflow fragmentation in future sessions
```

## Status Workflow

### lane-backlog (`status: open`)
- Created by retrospective skill
- Awaiting user review
- Scrum (dedup) pass runs before user sees cards: `bd --db .beads/retro.db list -l lane-backlog --json`

### lane-approved (`status: open`)
- User has approved: `bd --db .beads/retro.db update <id> --remove-label lane-backlog --add-label lane-approved`
- Ready for implementation

### lane-in-progress (`status: in_progress`)
- Claimed by implementer: `BD_ACTOR=<agent> bd --db .beads/retro.db update <id> --claim --add-label lane-in-progress`

### Closed (done)
- Implementation complete: `bd --db .beads/retro.db close <id> --reason "Implemented: [summary]"`
- Closed beads are queryable: `bd --db .beads/retro.db list -s closed --json`

### Rejected
- `bd --db .beads/retro.db close <id> --reason "Rejected: [reason]"`
- Closed beads serve as historical record; query with `bd --db .beads/retro.db search "<term>"`

---

## Notes

- **All cards are proposals, not commands**: Team lead reviews, user approves before implementation
- **Evidence required**: Every card must cite sources; never propose without evidence
- **Institutional memory**: Rejected cards kept with reasons; prevents repeat proposals
- **Cross-session tracking**: Action cards enable trend analysis (e.g., "How many IMPROVE cards target skills vs. protocols?")
- **Card reuse**: If same issue proposed multiple times, consolidate evidence and increase source_count

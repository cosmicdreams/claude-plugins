# Retro-Kanban — Retrospective Actions Board

Board-specific rules for `kanban/retrospective-actions/`. Read `sprint:kanban` first for universal standards that apply to all boards.

**Board path:** `kanban/retrospective-actions/`
**Purpose:** Process improvement cards generated by retrospectives — proposed by the retro, reviewed by team-lead, approved by user, implemented by agents.

---

## UI Mode

For reviewing and managing cards interactively, launch the kanban board UI instead of using
`AskUserQuestion`. The UI removes the 4-card-per-call limit and supports inline editing of card
fields, direct lane moves, and comment threading.

### When to use UI mode

- User says "open board", "launch ui", "show kanban", or similar
- More than 4 cards need review in a single session
- User wants to edit card fields (title, sections, frontmatter) directly

### Launch command

```bash
SPRINT_VERSION=$(ls ~/.claude/plugins/cache/local/sprint/ 2>/dev/null | sort -V | tail -1)
if [ -z "$SPRINT_VERSION" ]; then
  echo "ERROR: sprint plugin not installed"
  exit 1
fi
KANBAN_SERVER=~/.claude/plugins/cache/local/sprint/$SPRINT_VERSION/tools/kanban-ui/server.js

# Resolve the kanban board root (default: look for kanban/ relative to cwd)
BOARD_DIR="$(pwd)/kanban/retrospective-actions"
if [ ! -d "$BOARD_DIR" ]; then
  echo "ERROR: kanban/retrospective-actions not found at $(pwd)"
  exit 1
fi

node "$KANBAN_SERVER" \
  --dir "$BOARD_DIR" \
  --name "Retrospective Actions" \
  --lanes "1_backlog,2_approved,3_in-progress,4_done" \
  --port 3748 &

echo "Board PID: $!"
```

Tell the user:

> **Retro kanban board is open in your browser.**
>
> Review and manage cards directly in the UI:
> - **Move cards** between lanes with the -> arrow buttons
> - **Edit cards** (title, sections, priority) with the pencil button
> - **Add comments** from the edit panel
>
> Changes are written to disk immediately. When done, close the browser tab and say
> **"close board"** or just continue working — the server runs in the background.

### Fallback (AskUserQuestion mode)

When the UI cannot be launched (e.g., plugin not installed, no kanban directory), fall back to
the `AskUserQuestion` review flow documented in [## User Review Flow (Fallback — CLI Mode)] below.

## Directory Structure

```
kanban/retrospective-actions/
├── 1_backlog/        ← Created by retro; scrum/dedup runs here, then presented to user
├── 2_approved/       ← User approved; ready for implementation
├── 3_in-progress/    ← Actively being worked
└── 4_done/           ← Implementation complete and verified (terminal)
```

Numbered prefixes make `ls` output reflect workflow order.

---

## Card Naming Convention

```
retro-YYYYMMDD-NNN.md
```

Examples:
- `retro-20260221-001.md` — first card from 2026-02-21 retro
- `retro-20260221-007.md` — seventh card

Increment NNN sequentially per session (not per status directory).

---

## Card Format

See `retro:session` (references/action-card-template.md) for the full template.

Required frontmatter:

```yaml
---
id: retro-YYYYMMDD-NNN
session: YYYY-MM-DD
target: skill        # memory | claude-md | agent | skill | protocol | standard | future
category: improve    # keep-doing | improve | learn
priority: High       # Critical | High | Medium | Low
effort: M            # S (<1 hr) | M (1-4 hrs) | L (4+ hrs)
source_count: 2
source_weight: High  # Critical (4+) | High (2-3) | Medium (1)
created_date: YYYY-MM-DD
---
```

Required body sections: `## Finding`, `## Sources`, `## Recommendation`, `## Effort`, `## Priority`

## Creating Cards

1. Generate card ID: `retro-YYYYMMDD-NNN` (increment NNN for each new card this session)
2. Write card to `1_backlog/`
3. Run scrum (dedup pass) — see below
4. Present the cleaned set to the user directly from `1_backlog/`

New cards always start in `1_backlog/`. Never write directly to `2_approved/`.

---

## Scrum (Dedup Pass)

Before presenting cards to the user, run a dedup pass across all `1_backlog/` cards:

1. Read all `1_backlog/*.md` cards together
2. Identify near-duplicates (same finding, same target, similar recommendation)
3. Merge duplicates: fold evidence from redundant cards into the best card, delete redundant files
4. Present the cleaned set to the user directly from `1_backlog/`

Goal: present the user with a clean set of distinct, actionable cards. The scrum is an activity (a review pass), not a board status.

## User Review Flow (Fallback — CLI Mode)

> **Prefer UI mode** when available. This flow is the fallback when the kanban UI cannot launch.

### Fast-Path Criteria

A card qualifies for "Apply Now" if ALL of the following are true:
- Pure wording or description change — no new steps, gates, or behavioral requirements
- ≤ 5 lines of diff
- Single file, no cross-file dependencies
- Change is immediately verifiable by reading the diff alone

Present each reviewed card to the user via `AskUserQuestion` with markdown previews (max 4 cards per call):

```
Question: "Action Card: [card title]"
Options:
  - "Approve" (description: "Move to 2_approved/, ready for implementation")
    markdown: |
      **ID**: retro-YYYYMMDD-NNN
      **Category**: keep-doing | improve | learn
      **Target**: memory | skill | protocol | ...
      **Priority**: Critical | High | Medium

      **Finding**: [1-2 sentence summary]
      **Recommendation**: [what to do]
      **Effort**: S | M | L
  - "Apply Now" (description: "Trivial fix — apply immediately and move to 4_done/ this session")
    [Only offer this option when the card meets all fast-path criteria above]
  - "Reject" (description: "Delete card — not aligned with current direction")
  - "Modify" (description: "Discuss changes before deciding")
```

After user decisions:
- **Approved**: `mv 1_backlog/<card>.md 2_approved/<card>.md`
- **Apply Now**: Apply the change immediately, then `mv 1_backlog/<card>.md 4_done/<card>.md` — fill in `completed_date` and `Implementation.notes`
- **Rejected**: `rm 1_backlog/<card>.md` — log rationale in retro report
- **Modified**: Edit card in `1_backlog/`, then move to `2_approved/`

User may identify missing cards during review — create them directly in `2_approved/`.

---

## Implementation Lifecycle

After a card is in `2_approved/`:

1. Agent claims it: moves to `3_in-progress/`, sets `assignee` in frontmatter
2. Agent implements the change
3. Verified complete: team-lead moves to `4_done/`

`4_done/` is terminal. Cards in `4_done/` are kept as institutional memory — they are not deleted.

### Verification Gate (discipline-enforcement cards)

Cards with `verification_required: true` in frontmatter **cannot move to `4_done/`** until `verification_evidence` is filled in.

`verification_evidence` must contain: sprint name or date, agent name, and a transcript snippet or observation confirming the gate was followed at least once.

Without this evidence, the change may have been written but not adopted. Closing the card without evidence claims success you cannot support.

---

## Rejection Note

Per the universal rule (`sprint:kanban`), rejected cards are deleted. Exception for retro cards:

Rejected cards **may be kept in `1_backlog/`** with a note documenting the rejection reason if the reason has strategic memory value (e.g., "We're removing jQuery, don't invest in understanding it — retro 2026-02-21"). Future retros can check rejection history to avoid re-proposing superseded ideas.

Default: delete rejected cards unless the rejection reason reveals strategic direction worth preserving.

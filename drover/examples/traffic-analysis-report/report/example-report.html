Three distinct budgets are at play

As a reminder we have three consumption concerns items below. Our efforts in optimizing traffic has been to improve the performance of all three.

Acquia Views & Visits (V&V)

Contract metering against Acquia Cloud Platform. Counted at the Varnish layer.

Counts:

  • Dynamic HTTP 2xx responses that bootstrapped Drupal
  • Varnish cache hits where the underlying request originally bootstrapped Drupal

Does NOT count:

  • Static assets — CSS, JS, images, fonts, PDFs delivered from filesystem
  • All 3xx redirects
  • All 4xx client errors (404, 403, etc.)
  • Major known bots — Googlebot, Bingbot, Yandex, Applebot, LinkedInBot, facebookexternalhit, GPTBot, DuckDuckBot, Baidu, CCBot, AhrefsBot, SemrushBot, Slurp, Twitterbot, SiteMonitor, and many more

SearchStax search-query quota

A different contract metering — the search index has its own monthly query budget.

Counts:

  • Every SearchStax query, regardless of who triggered it
  • No bot exclusion at the SearchStax layer — Bingbot, Googlebot, scrapers, and humans all consume from the same pool
  • Faceted listings and area searches that drive SearchStax queries on the back end

Does NOT count:

  • Search-result pages served entirely from Drupal's render cache without re-querying SearchStax
  • SearchMediator manifest endpoints (those are static JSON, not SearchStax-backed)

Origin server CPU & bandwidth

Not a contract meter — but real load on the Acquia origin servers.

Counts:

  • Every single request that reaches the origin server, regardless of response code
  • Static assets that Imperva does not cache at the edge
  • 4xx and 5xx responses, including the 403s from the May 15 mitigation (cheap, but non-zero)
  • Bot and scraper traffic — bots that are excluded from V&V still cost CPU/bandwidth here

Tightening this budget keeps response times healthy and avoids overrunning the underlying server capacity (separate from billing).

TL;DR:
  • The Views & Visits story is the AWS scraper — it presented as a real browser so Acquia counted every one of its successful hits. The May 15 mitigation is a large V&V relief.
  • The SearchStax story is mostly Bingbot now — but Bingbot is an excluded V&V bot, so this is purely a search-quota issue, not a billing-page issue.
  • The origin CPU/bandwidth story includes everything else — static assets reaching origin, 4xx attack-scanner noise, the 5,400/day post-mitigation scraper probes that get 403'd, etc.

Why static assets matter (and where they don't)

The 163,674 static asset requests (JavaScript, stylesheets, images, fonts, PDFs) that reached the origin are cacheable by definition. They should resolve at Imperva's edge and never touch Acquia. Tightening Imperva's cache rules — honoring origin Cache-Control headers and adding extension-based caching for the standard static types — eliminates this entire class of passthrough.

Budget impact: Origin CPU/bandwidth No V&V impact — static assets are explicitly excluded from Acquia's Views & Visits count, because they are delivered from the filesystem without bootstrapping Drupal. Edge-caching them does not reduce V&V; it reduces origin load and improves response times. Do not pursue this rule expecting V&V relief — pursue it for performance and to keep CPU headroom available for the requests that do count.

09 The robots.txt fix — now the single most impactful remaining change

With the AWS scraper blocked, Bingbot is the largest remaining contributor to the SearchStax burn (57,765 search hits, ~2,300/day). Microsoft honors robots.txt scrupulously. The current Acmecorp robots.txt already attempts to disallow search routes but does so with a directive that does not match the URLs actually being crawled. Fixing it is a one-line-per-route change with no impact on the ad-campaign pages.

The current rule is broken

Today's robots.txt contains: 

Disallow: /search/

The trailing slash matters. /search/ is interpreted as a path prefix that requires a literal slash after search. It does not match:

  • /search (no trailing slash)
  • /search?keys=... (the actual search query URL)
  • /north-terminal/search and the other area searches

This is why 50,756 declared-bot hits reached the bare /search page despite the existing rule. The bots obeyed robots.txt — the rule just did not cover the right URLs.

The corrected rule (drop-in replacement)

Replace the single broken line with the seven specific Disallow directives below. This covers every SearchStax-burning route observed in the logs and leaves the SearchMediator-driven pages fully open: 

User-agent: *
Disallow: /search
Disallow: /search?
Disallow: /transit/search
Disallow: /north-terminal/search
Disallow: /south-terminal/search
Disallow: /east-station/search
Disallow: /west-station/search
Disallow: /central-hub/search

Removing the trailing slash makes the rule match both the bare path and any query string. Each area search is listed explicitly so the intent is unambiguous to crawlers.

What is deliberately not blocked

The pages SearchMediator powers — the ones carrying ad-campaign deep links — must stay crawlable for organic search visibility. The proposed robots.txt does not touch any of them:

11 Method & Caveats

How the data was produced

Production apache-access logs were pulled from Acquia for each day in the May 1–25, 2026 window via the drover Acquia-pull skill (one process per day per the known multi-day pull bug; each file's distinct md5 and dominant date were verified). Five reusable Python analyzers run against the per-day gzipped logs: analyze.py for actor and search aggregates, route_breakdown.py for per-route splits, host_breakdown.py for the Host-header analysis behind Section 05, timeline.py for the per-day cliff chart in Section 02, and enrichment.py for the bytes-by-actor and named-bot tables. May 26 was excluded as a partial day still rotating.

Requests are classified by user-agent and source IP. Declared bots are matched on well-known crawler user-agent strings. The suspected scraper class is a heuristic combining the headless Chrome signature with datacenter Autonomous System Numbers. Humans are the residual after subtracting the other classes. The Host-header analysis uses the host= field that Acquia's log format records on every line, distinct from the internal Apache vhost=.

What this report does not yet answer

Quota tie-out: the percentages above are a request-side proxy. The true SearchStax search-quota burn requires the May query count and the monthly limit from the live SearchStax dashboard.

Scraper attribution: the AWS actor has not been identified by name. Before a hard block under Rule 1, reverse-DNS the ranges and check for any sanctioned first-party or partner integrations that legitimately run on AWS.
